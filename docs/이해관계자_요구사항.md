# 이해관계자 요구사항

## 목적

웹 앱 개발에 앞서 이해관계자가 원하는 결과와 필요한 기능을 정리한다. 확인된 요구와 아직 확인이 필요한 후보를 구분한다.

## 이해관계자

| 이해관계자 | 역할 | 확인된 요구 |
|---|---|---|
| 대표님 / 운영자 | 참가 신청부터 행사 후 피드백까지의 운영 담당 | 기본적인 운영 업무 전반을 자동화하고, 예외적인 상황만 직접 처리하길 원한다. 전반적인 수기 작업과 참가자 문의에 건별로 답하는 일이 번거롭다고 말했다. 신청부터 행사 안내까지는 예외 상황을 제외하고 운영자 없이 진행되길 원한다. |
| 참가자 | 신청·매칭·행사 안내·피드백의 이용자 | 아직 직접 확인한 요구사항 없음 |

## 대표님 요구사항

### 확인된 상위 요구

- 수기로 처리하는 기본 운영 업무 전반을 자동화하고 싶다.
- 정상적인 운영 흐름은 자동 처리하고, 자동으로 해결하기 어려운 예외 상황은 운영자가 처리하는 방향을 원한다.
- 참가자 문의에 매번 개별 답변하는 부담을 줄이고 싶다.
- 신청부터 행사 안내까지는 예외 상황을 제외하고 운영자 없이 진행되길 원한다. (대표님 확인)

## 요구사항 우선순위 (PRD P0·P1·P2 기준)

우선순위는 PRD 6장의 구분을 따른다. **1순위 = P0(필수), 2순위 = P1(권장), 3순위 = P2(후속)**이며, PRD는 P0 흐름을 처음부터 끝까지 시연할 수 있어야 한다고 정하므로 1순위 전체를 MVP 범위로 본다. 각 기능의 상세 완료 조건은 PRD의 기능 ID를 참조한다.

**핵심 흐름 (PRD 5장):** 회원가입·프로필 → 날짜·지역 선택 → 이용권·결제 → 자동 매칭·재배치·확정 → 식당 배정·단체방·안내 → 리마인드 → 식사·대화 콘텐츠 → 피드백 → 다음 일정 추천. 운영자는 회차·식당을 설정하고, 자동화되지 못한 예외와 안전 신고만 처리한다.

### 1순위 — P0 필수 (MVP)

| 기능 묶음 | PRD ID | 이해관계자 요구와의 연결 |
|---|---|---|
| 회원가입·프로필 | ACC-01~05 | 매칭에 필요한 정보(MBTI·관심사·성향 등)를 신청 단계에서 받음 |
| 일정 선택·신청·모의 결제 | APP-01~04, PAY-01~03 | Google Forms·입금 확인 등 흩어진 신청 업무를 한곳으로 통합 |
| 매칭 상태와 대체 일정 | STA-01~06 | 진행 상태를 알기 어려운 참가자 문제와 반복 문의를 줄임 |
| 자동 매칭·재배치·확정 | MAT-01~13 (규칙은 PRD 7장) | 대표님의 "예외 외에는 운영자 없이" 요구의 핵심 |
| 확정 안내·식당 배정·단체방·리마인드 | INF-01~08 | 수기 안내와 식당 배정 업무를 자동화 |
| 대화 콘텐츠 | CON-01~03 | 행사 당일 운영 부담을 줄임 |
| 피드백·안전·재방문 | FDB-01~04, SAF-01~02, RET-01~02 | 피드백과 이전 만남을 다음 매칭에 반영. 피드백은 운영자만 열람 |
| 운영자 설정 | PRD 5장 운영자 흐름 1·2, MAT-15 | 회차·마감일, 식당·수용 인원, 자동화 규칙, 매칭 가중치·최소 점수 사전 설정 |

### 2순위 — P1 권장

ACC-06 프로필 재사용, STA-07 대기자 자동 전환, MAT-14 운영자 긴급 수정(확정 후 취소·안전 문제 시 참가자 이동 등, 변경 이력 기록), CON-04 콘텐츠 관리, RET-03 이용권 관리

### 3순위 — P2 후속

MAT-16 학습형 추천

### 운영자 예외

정상 흐름은 자동 처리하고, PRD가 운영자에게 넘기도록 정한 건만 운영자가 처리한다. 인원 부족·조건 미충족은 예외가 아니라 자동 재배치 → 대체 일정 제안(STA-03~06)으로 처리한다.

- 결제 오류, 데이터 누락, 식당 부족, 해결되지 않은 조건 충돌 (MAT-13, INF-02)
- 안내·리마인드 반복 발송 실패 (INF-08)
- 노쇼 후보 확인 (FDB-01)
- 안전 신고 검토와 제한 조치 (SAF-02)
- 확정 후 취소·안전 문제로 인한 수동 조정 (MAT-14, 2순위)

### PRD와 다르게 정하거나 보류한 항목

| 항목 | 결정 |
|---|---|
| 결제·환불 | PRD가 허용한 모의 구현으로 진행. 실결제 연동(PAY-04, P1)은 제외 |
| 이전에 만난 참가자 재배정 자체 금지 | 보류. PRD는 새로운 사람 우선(MAT-06)과 비선호 관계 제외(MAT-05)까지만 요구 |
| 카카오톡 등 외부 메신저 연동 | 불필요. PRD는 앱 내 단체방(INF-04) 요구 |
| 실제 식당 예약 연동 | 범위 밖. 식당 재고는 가상 데이터 |
| 대화형 챗봇 | 제외. 정해진 메시지 템플릿 자동 발송으로 안내 |
| 가중치·최소 점수 설정 (MAT-15, P1) | PRD 7.0·5장 운영자 흐름·17장 MVP 화면 목록에 따라 1순위(MVP)로 올림 |
| 앱 푸시 알림 (INF-01·07) | 웹 앱이므로 앱 내 알림과 단체방 시스템 메시지로 대체 |
| 확정 후 취소 시 대기자 자동 충원 (PRD 15장, STA-07) | P1이므로 MVP 제외. 4명 이상 남으면 테이블 유지, 4명 미만이 되면 남은 참가자 자동 재배치(MAT-08)만 적용 |

## 우선순위 결정 시 유의점

- 우선순위는 PRD 6장의 P0·P1·P2 구분을 따르며, 1순위(P0) 전체가 해커톤 MVP 범위다. PRD는 P0 흐름을 처음부터 끝까지 시연할 수 있어야 한다고 정한다.
- MVP의 성공 기준은 참가 신청부터 매칭 및 행사 안내까지의 기본 흐름이 예외 상황을 제외하고 운영자 개입 없이 완료되는지로 둔다. (대표님 확인)
- 결제·환불은 PRD가 허용한 대로 모의 구현하며, 실제 청구나 환불은 발생하지 않는다. 실결제 연동(PAY-04)은 제외한다.
- 1순위 안의 구현 순서는 `MVP_기능_범위.md` 6장을 따른다.
- 참가자의 직접 요구사항은 확인되지 않았으므로, 화면과 안내 문구는 사용성 검토 과정에서 확인한다.
- 참가자 안내는 PRD의 CS 자동화 요구에 따라, 대화형 챗봇이 아니라 상태와 상황에 맞춘 정해진 메시지 템플릿을 자동 발송하는 방식으로 한다.
