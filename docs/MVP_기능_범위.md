# MVP 기능 범위

## 1. 문서 목적

참가자용 모바일 웹앱과 운영자 웹의 첫 구현에서 무엇을 만들고 무엇을 제외할지 합의하기 위한 문서다. PRD의 P0 기능을 MVP 범위로 삼되, 대표 기능인 **참가 신청부터 자동 매칭과 행사 안내까지**를 우선 구현·시연한다.

## 2. MVP 목표

참가자가 앱에서 신청하고 결제 상태를 확인하면, 시스템이 정해진 규칙으로 참가자를 매칭하고 식당·단체방·행사 안내를 자동으로 준비한다. 정상 흐름은 운영자 개입 없이 진행하며, 시스템이 해결하지 못한 예외만 운영자가 확인한다.

### 주요 사용자

- **참가자:** 모바일 웹브라우저에서 웹앱 링크로 접속해 프로필을 작성하고 회차를 신청한 뒤 매칭 결과와 행사 정보를 확인한다.
- **운영자:** 회차와 가상 식당 정보를 사전 등록하고, 자동 처리 결과와 해결되지 않은 예외를 확인한다.

## 3. 정상 흐름과 예외 흐름

### 정상 흐름

결제 완료 → 자동 매칭 → 필수 조건 확인 → 자동 확정 → 가상 식당 배정 → 안내·단체방·리마인드 → 식사·피드백 → 다음 일정 추천 순으로 처리한다. 운영자는 회차·식당·자동화 기준을 미리 설정하고, 정상 흐름에는 개입하지 않는다.

### 자동 예외 처리

최초 배치가 4명 미만이거나, 필수 조건을 만족하지 못하거나, 최소 매칭 점수에 못 미치면 아래 순서로 재배치한다(PRD 7.0·7.4).

1. 같은 날짜·같은 희망 지역의 다른 미확정 테이블
2. 같은 날짜·참가자가 선택한 다른 희망 지역의 미확정 테이블
3. 참가자가 선택한 다른 날짜·같은 희망 지역의 미확정 테이블
4. 참가자가 선택한 다른 날짜·다른 희망 지역의 미확정 테이블
5. 후보가 없으면 아직 선택하지 않은 모집 일정 중 조건에 맞는 회차를 추천하고, 참가자가 동의한 경우에만 이동한다.
6. 이동하지 않거나 적합한 회차가 없으면 이용권 보관 또는 환불을 선택하도록 안내한다.

재배치 중에도 연령·차단·신고 등 필수 조건은 완화하지 않는다. 한 참가자를 동시에 여러 테이블에 배치하지 않으며, 재배치와 조건 검증이 끝난 뒤에만 테이블을 확정한다.

### 운영자에게 넘기는 예외

자동 처리와 재시도 후에도 해결되지 않은 결제 오류·데이터 누락·조건 충돌·식당 배정 실패·반복 안내 발송 실패를 예외 목록에 올린다. 안전 신고와 노쇼 후보도 운영자가 확인한다. 인원 부족이나 최초 조건 미충족은 먼저 자동 재배치로 해결하므로, 그 자체만으로 운영자 예외가 되지 않는다. 확정 후 취소가 발생하면 남은 테이블의 필수 조건을 다시 검증한다. 남은 인원이 4명 이상이고 필수 조건을 충족하면 테이블을 그대로 유지한다. 4명 미만이 되면 PRD 15장에 따라 남은 참가자를 자동 재배치 규칙(MAT-08)으로 다른 미확정 테이블에 다시 배치하고, 재배치에 실패한 참가자에게는 대체 일정·이용권 보관·환불 선택지를 안내한다. 대기자 자동 충원(STA-07)은 P1이므로 MVP에서 제외한다. 재배치 후에도 해결되지 않은 건만 운영자 예외로 올린다.

## 4. MVP에 포함할 기능

| 영역 | MVP 범위 | 핵심 완료 기준 |
|---|---|---|
| 계정·프로필 | 테스트 계정 로그인, 기본 정보, 매칭 선호, 식사 조건, 필수 동의 | 매칭에 필요한 정보를 등록하고 신청 전에 누락 여부를 확인한다. |
| 회차·신청 | 모집 회차 확인, 가능한 날짜와 지역(서울 4개 지역) 선택, 신청서 제출 | 참가자가 모집 중인 회차를 선택해 신청을 완료한다. |
| 이용권·결제 | 1회권(9,900원)·멤버십(1·3·6개월) 선택, 모의 결제, 결제·환불 상태 표시, 결제 전·신청 완료 화면의 환불 규정·노쇼 정책 표시 | 실제 청구 없이 결제 상태가 신청과 매칭 흐름에 반영된다. |
| 매칭 상태·대체 일정 | 신청·결제·매칭 상태와 안내 예정 시점 표시, 확정·재배치·실패 이유 표시, 실패 시 대체 일정·이용권 보관·환불 선택 | 참가자가 현재 상태와 다음 행동을 앱에서 확인한다. 다른 참가자의 개인정보나 상세 점수는 보이지 않는다. |
| 자동 매칭 | 마감 시 결제 완료자를 대상으로 매칭하고 테이블을 자동 검증·확정 | 날짜·지역이 맞고 4~6명이며, 한 테이블의 나이 차이가 8살 이내인 조합만 확정한다. 차단·신고·비선호 관계는 제외한다. |
| 자동 재배치 | 4명 미만·필수 조건 미충족·최소 매칭 점수 미달 조합을 신청자가 선택한 다른 날짜·지역 범위에서 재배치, 7명 이상 후보군 분리와 미완성 테이블 병합 | 가능한 테이블을 탐색한 뒤 실패하면 대체 선택지를 안내한다. 필수 조건은 완화하지 않는다. |
| 식당·안내 | 가상 식당 재고에서 자동 배정, 매칭 확정 안내, 단체방 생성, 시스템 공지와 리마인드, 발송 실패 시 자동 재시도 | 확정 결과, 식당 정보와 행사 안내가 참가자에게 앱 안에서 전달된다. 확정 전에는 다른 참가자의 개인정보를 공개하지 않고, 확정 후에도 제한된 소개만 보여준다. |
| 행사 중·후 | 공통 관심사 기반 대화 주제(최소 3개)와 아이스브레이킹 자동 게시, 체크인, 만족도·재참여 의향·사람별 선호, 신고·차단, 참가 이력과 다음 일정 추천 | 행사 참여와 피드백이 기록되고, 신고·비선호 관계가 다음 매칭에서 고려된다. 참가자는 다음 일정을 추천받는다. |
| 운영자 화면 | 회차·가상 식당 사전 설정, 매칭 가중치·최소 점수 설정(MAT-15), 신청·매칭 결과 및 예외 목록 확인, 노쇼 후보 확인, 신고 검토와 제한 조치 | 정상 흐름은 자동 진행되고 처리되지 않은 결제·데이터·식당·조건 예외, 반복 발송 실패, 노쇼 후보, 안전 신고만 운영자에게 표시된다. |

## 5. 매칭 기준

- **필수 조건:** 결제 완료, 날짜·지역 조건 일치, 테이블 4~6명, 연령 차이 8살 이내, 차단·신고·비선호 관계 제외.
- **선호 반영 순서:** 연령대 → 성비 → MBTI 궁합 → 관심사 → 만나고 싶은 사람.
- 필수 조건이 맞지 않으면 해당 조합을 확정하지 않고 자동 재배치를 시도한다.
- 필수 조건은 충족하지만 최소 매칭 점수에 못 미치면 확정하지 않고, 다른 테이블 재배치 또는 대체 일정 안내로 전환한다. (PRD 7.0)
- 결제를 완료하지 않은 신청자는 매칭 후보에서 제외하고 결제 기한을 안내한다. (PRD 15장)
- 이전에 만난 참가자는 우선 새로운 사람과 매칭하되, 재배정 자체를 금지하는 규칙은 두지 않는다.
- 최소 매칭 점수와 항목별 가중치는 운영자가 회차별 또는 서비스 전체 설정으로 관리한다(PRD 7.0). 설정 기능(MAT-15)은 6장 기능 표에서 P1이지만, PRD 5장 운영자 흐름 2와 17장 MVP 화면 목록(식당 재고·자동화 규칙 관리)에 포함되어 있어 MVP에 넣는다. 아래 값은 운영자 설정 화면의 초기값이다.

### 가중치와 최소 점수 초기값

100점 만점이며, **최소 매칭 점수의 초기값은 55점**으로 둔다. 운영자는 항목별 가중치와 최소 점수를 운영자 화면에서 바꿀 수 있다. 가중치는 PRD MAT-04의 우선순위 순서를 따른다.

| 항목 | 가중치 | 항목 점수 계산 (0~1) |
|---|---|---|
| 연령 근접도 | 25 | 테이블 내 나이 차 3살 이하 1, 5살 이하 0.75, 8살 이하 0.5 |
| 성비 | 22 | 남녀 수 차이 1명 이하 1, 2명 0.5, 3명 이상 0.25, 한 성별만 0 |
| MBTI 궁합 | 18 | 두 사람씩 짝지어 S/N이 같으면 0.5, E/I가 다르면 0.5를 더한 값의 평균 (팀 결정 규칙) |
| 공통 관심사 | 15 | 공통 관심사가 2개 이상인 두 사람 짝의 비율 |
| 만나고 싶은 사람의 성향 | 10 | 각자 원한 성향이 테이블에 있는 비율의 평균 |
| 새로운 사람 비율 | 10 | 이전에 만난 적 없는 두 사람 짝의 비율 |

**근거 (`우연한식탁_가상데이터.xlsx` 시뮬레이션, 291명):** 설문 응답 294건 중 희망 지역에 서울 4개 운영 지역이 하나도 없는 3건(엑셀 67행 인천, 164행 수원 인계동, 221행 분당·판교)을 운영 지역 정책(6장)에 따라 제외했다.

| 최소 점수 | 확정 테이블 | 매칭 성공 | 실패 |
|---|---|---|---|
| 기준 없음 | 41 | 210명 | 81명 |
| 50 | 41 | 210명 | 81명 |
| **55** | **40** | **204명** | **87명** |
| 60 | 37 | 187명 | 104명 |
| 70 | 32 | 154명 | 137명 |

- 기준이 없어도 약 28%가 날짜·지역별 인원 부족과 연령 조건 때문에 실패한다. 55점은 실패를 6명만 늘리면서 점수가 낮은 조합을 거른다.
- 처음 검토한 계산식(연령 1 − 나이 차 ÷ 8, 공통 관심사 1개 이상)은 연령 점수가 거의 0이 되고 관심사 점수는 거의 만점이 되어 변별력이 없어 위와 같이 조정했다.
- 가상 데이터에는 결제 상태와 이전 만남 이력이 없어 전원 결제 완료, 새로운 사람 비율 만점으로 계산했다. 매칭 방식은 날짜순으로 테이블을 채우는 단순화한 방식이므로, 절대 수치보다 기준 간 비교 용도로 본다.
- MBTI 궁합 기준은 PRD에 없어 팀이 정했다(주최 측 답변: 참가자가 직접 정함).

## 6. 운영 정책 (주최 측 답변 반영·팀 결정)

PRD에 정해지지 않은 운영 정책은 해커톤 주최 측(Blaybus) 답변에 따라 팀이 정한다. "주최 측 확정"은 답변으로 정해진 사항, "팀 결정"은 PRD 원칙(7.3, 15장, SAF-02) 안에서 팀이 정한 사항이다.

| 항목 | 정책 | 구분 |
|---|---|---|
| 앱 형태 | 참가자 앱은 설치형 앱이 아닌 **모바일 웹브라우저용 웹앱**으로 배포하고, 심사는 배포 링크로 진행한다. | 주최 측 확정 |
| 운영 지역 | 서울 4개 지역(홍대/합정, 잠실, 강남/신논현, 을지로/종로)만 신청을 받는다. 지역은 지도 경계가 아니라 이 4개 선택지로 관리하며, 회차·식당·매칭 후보군·재배치·일정 추천 모두 이 4개 안에서만 처리한다. 서울 안이라도 4개 지역 밖은 선택할 수 없다. | 주최 측 확정 |
| 그 외 지역 수요 | 기존 설문의 '기타' 지역은 신청 선택지로 두지 않는다. 대신 선택 항목으로 "다른 지역 오픈 알림 받기"(희망 지역 자유 입력)를 두고, 매칭에는 쓰지 않으며 운영자가 지역 확장 수요로만 확인한다. 4개 지역을 하나도 고르지 않으면 "현재 운영 지역이 아니며, 오픈하면 알려 드린다"고 안내한다. PRD에 없는 기능이므로 2단계 선택 기능으로 둔다. | 팀 결정 |
| 식당 데이터 | 가상 식당 데이터에 지역, 수용 인원, 예약 가능 여부와 함께 리뷰 평점을 넣고, 평점이 좋고 예약 가능한 식당을 우선 배정한다. | 주최 측 기준 반영 |
| 운영자 사전 검토 | 신청자를 운영자가 검토·선정하는 단계는 두지 않고, 자동 매칭·자동 확정한다. | 주최 측 확정 |
| 이용권 가격 | 1회권 9,900원 / 멤버십 1개월 35,000원, 3개월 75,000원, 6개월 120,000원 | 주최 측 확정 |
| 멤버십 이용 | 기간 안에 횟수 제한 없이 신청할 수 있다. 매칭에 실패하면 실패 1회당 이용 기한을 1주(1회차) 연장한다. | 주최 측 확정 (연장 단위 1주는 팀 결정) |
| 멤버십 매칭 실패 선택지 | 대체 일정 이동 또는 기한 연장 중 선택한다. 멤버십에는 회당 환불을 적용하지 않는다. | 팀 결정 |
| 환불 마감 | 행사(목요일) 직전 **화요일 24:00** 이후 환불 불가. 자동 매칭 마감 시각도 화요일 24:00으로 맞춘다. | 환불 시점은 주최 측 확정, 매칭 마감 일치는 팀 결정 |
| 마감 전 취소 | 매칭 마감(화요일 24:00) 전에는 아직 테이블이 확정되지 않았으므로 신청 취소(신청 상태 CANCELED)로 처리한다. 1회권은 모의 환불하고, 멤버십은 신청만 취소한다. | 팀 결정 |
| 마감 후·당일 취소 | 매칭 마감 이후의 취소는 모두 확정 후 취소다. 앱에서 취소 요청은 받되(인원 변동을 남은 참가자에게 알리기 위함) 환불하지 않고 CANCELED_LATE로 기록한다. 당일 취소는 노쇼와 같이 이용 제한 횟수에 포함한다. | 팀 결정 |
| 노쇼 처리 | 행사 종료 시각까지 체크인하지 않으면 노쇼 후보가 되고(FDB-01), 운영자가 확인하면 NO_SHOW로 확정한다. 1회권은 사용된 것으로 처리하고 환불하지 않는다. | 팀 결정 |
| 이용 제한 단계 | 노쇼·당일 취소 누적 1회 경고, 2회 4주 참가 제한, 3회 영구 제한. 시스템이 누적 횟수에 따라 단계를 제안하고 운영자가 확정한다(SAF-02). | 팀 결정 |
| 확정 후 3명 이하 | 4명 이상 남으면 유지, 4명 미만이 되면 남은 참가자를 자동 재배치하고 실패 시 대체 일정·이용권 보관·환불(멤버십은 기한 연장) 선택지를 준다. 매칭 불가로 인한 환불이므로 환불 마감 이후에도 환불을 허용한다. | 팀 결정 (PRD 7.3·15장 원칙) |
| 성비 | 필수 조건이 아닌 선호 조건이므로 한 성별만 있거나 한 명만 다른 성별인 테이블도 허용하고, 성비 점수로만 반영한다. | 팀 결정 |
| MBTI 궁합 | 두 사람씩 짝지어 S/N이 같으면 0.5, E/I가 다르면 0.5를 더한다(5장). | 팀 결정 |

## 8. 상태값과 비기능 요구사항

### 상태값 (PRD 12장)

신청·결제·매칭·참석 상태를 하나의 값으로 합치지 않고 분리해 저장한다.

| 구분 | 상태값 |
|---|---|
| 신청 | DRAFT, SUBMITTED, CANCELED |
| 결제 | PENDING, PAID, FAILED, REFUND_AVAILABLE, REFUND_REQUESTED, REFUND_PROCESSING, REFUNDED, REFUND_FAILED |
| 매칭 | WAITING, MATCHING, REALLOCATING, CONFIRMED, ALTERNATIVE_OFFERED, TRANSFERRED, NO_MATCH, EXCEPTION |
| 참석 | SCHEDULED, ATTENDED, CANCELED_EARLY, CANCELED_LATE, NO_SHOW |

### 비기능 요구사항 (PRD 7.3·16장)

- **사용성:** 모바일 화면을 우선 설계한다. 프로필 입력을 포함한 최초 신청은 5분 안에 끝나야 한다. 참가자는 홈 화면에서 현재 신청·결제·매칭 상태를 바로 확인하고, 실패·대기 상태에서도 다음 행동을 한 화면에서 선택할 수 있어야 한다.
- **중복 방지:** 같은 매칭 작업이 여러 번 실행돼도 중복 테이블·중복 환불·중복 단체방이 생기지 않아야 한다. 같은 참가자를 두 테이블에 동시에 배치하지 않고, 일정 이동 시 결제가 중복 승인되지 않아야 한다.
- **개인정보·안전:** 연락처, 출생연도, 차단·신고, 사람별 선호는 운영상 필요한 사용자에게만 공개한다. 매칭 전에는 다른 참가자의 개인정보를 공개하지 않는다. 운영자 계정은 권한별 접근 통제를 적용하고 주요 변경 이력을 기록한다.
- **기록·추적:** 매칭 버전과 적용 기준, 생성·분리·병합·재배치·확정 결과, 자동 처리 실패 사유와 운영자 개입 이력, 메시지 발송 성공·실패와 재시도, 일정 이동·이용권 보관·환불 처리 결과, 주요 상태 변경의 시간과 변경 주체를 기록한다.
- **내보내기:** 참가자 목록과 테이블 결과를 CSV로 내보낼 수 있어야 한다.

## 10. 구현 순서

MVP 전체 범위(PRD 18장 12단계)는 줄이지 않되, 구현은 두 단계로 나눈다.

### 1단계 — 첫 시연 필수 흐름 (PRD 18장 1~8번, 12번)

신청부터 매칭 확정·행사 안내, 매칭 실패 처리, 운영자 예외 확인까지 한 번에 시연할 수 있는 최소 흐름이다. 매칭 가중치와 최소 점수는 초기값(5장)으로 고정한다.

1. **신청 흐름:** 로그인·프로필·회차·날짜·지역 선택·이용권·모의 결제·환불 규정 표시
2. **매칭 흐름:** 마감 시 자동 매칭·필수 조건 검증·최소 점수 확인·재배치·분리·병합·자동 확정·상태와 이유 표시
3. **확정 안내 흐름:** 가상 식당 배정·단체방 생성·확정 안내·발송 재시도
4. **매칭 실패 흐름:** 대체 일정 추천·일정 이동·이용권 보관·모의 환불·멤버십 기한 연장
5. **운영자 최소 기능:** 회차·가상 식당 사전 등록, 자동 처리 결과 조회, 예외 목록

### 2단계 — MVP 완료 범위 (PRD 18장 9~11번 추가)

1단계 흐름 위에 행사 전·중·후와 운영 관리 기능을 더한다.

6. **행사 전·중:** 행사 1일 전 리마인드, 대화 주제·아이스브레이킹 자동 게시
7. **행사 후:** 체크인·만족도·재참여 의향·사람별 선호·신고·차단, 참가 이력·다음 일정 추천
8. **다음 매칭 반영:** 이전 만남·비선호·신고 관계를 2회차 매칭에 반영
9. **확정 후 취소:** 테이블 유지 또는 남은 참가자 자동 재배치
10. **운영자 관리:** 매칭 가중치·최소 점수 설정 화면(MAT-15), 노쇼 후보 확인·이용 제한, 신고 검토, 운영 대시보드 지표, CSV 내보내기
11. **(선택) 다른 지역 오픈 알림:** 운영 지역 밖 희망 지역 입력과 운영자 수요 확인. PRD 외 기능이므로 다른 2단계 항목을 마친 뒤 여유가 있으면 구현한다.

각 단계는 앞 단계와 연결해 하나의 참가자 흐름으로 시연한다.

## 11. MVP 시연 완료 기준

PRD 18장 "해커톤 완료 조건"을 그대로 따른다. 아래 시나리오가 하나의 데모에서 끊김 없이 동작하면 MVP가 완성된 것으로 본다. **1단계(첫 시연)는 1~8번과 12번, 2단계(MVP 완료)는 9~11번까지 모두 통과해야 한다.**

1. 서로 다른 프로필을 가진 테스트 참가자들이 날짜·지역을 선택하고 신청한다.
2. 매칭 마감 시각이 되면 시스템이 결제 완료자를 대상으로 자동 매칭을 실행한다.
3. 시스템이 필수 조건과 우선순위에 따라 4~6인 테이블을 생성한다.
4. 4명 미만 또는 조건 미충족 조합을 해제하고 다른 적합한 테이블로 자동 재배치한다.
5. 조건 검증을 통과한 테이블을 운영자 승인 없이 자동 확정한다.
6. 지역·시간·인원에 맞는 식당을 자동 배정하고 앱 단체방을 자동 생성한다.
7. 참가자가 앱 단체방에서 매칭 결과, 식당, 큐레이션과 행사 안내를 확인한다.
8. 매칭되지 못한 참가자에게 다른 일정을 추천하고, 일정 이동 또는 환불 선택이 자동 처리되는 것을 확인한다.
9. 행사 전 리마인드와 행사 중 대화 콘텐츠가 자동 게시되는 것을 확인한다.
10. 행사 후 참가자가 체크인과 만족도·사람별 선호를 입력한다.
11. 다음 매칭에서 이전 만남과 피드백이 반영된 것을 확인한다.
12. 정상 시나리오 전체가 운영자 개입 없이 완료되고, 해결되지 않은 예외만 운영자 화면에 나타나는 것을 확인한다.

**팀 추가 확인 항목**

- 자동 재배치가 1~4순위 후보를 차례로 확인하고, 5순위의 미선택 일정은 참가자 동의를 받은 뒤에만 이동한다.
- 확정 후 취소가 발생하면 4명 이상 남은 테이블은 유지되고, 4명 미만이 된 테이블의 남은 참가자는 자동 재배치되거나 대체 선택지를 받는다.
- 멤버십 이용자가 매칭에 실패하면 이용 기한이 연장된다.

**시연 시나리오 준비:** 11번(이전 만남·피드백 반영)을 보여주려면 회차를 두 번 실행해야 한다. 1회차 참가자가 피드백을 남긴 뒤 2회차를 매칭해, 이전에 만난 사람보다 새로운 사람과 매칭되고 비선호 관계가 제외되는 것을 보여준다.

## 12. 근거 및 결정 사항

- 기능 우선순위와 완료 기준은 PRD의 P0·P1·P2 구분을 따른다. PRD는 P0 흐름의 처음부터 끝까지 시연을 완료 조건으로 둔다.
- 대표님이 확인한 요구는 기본 운영 자동화, 참가자 문의에 건별로 답하는 부담 완화, 예외 상황을 제외한 신청부터 행사 안내까지의 자동 진행이다.
- 참가자 요구사항은 직접 확인되지 않았다. 참가자 화면과 안내 문구는 시제품 검토 과정에서 확인한다.
- 매칭 가중치와 최소 점수는 운영자가 설정한다. 초기값(최소 55점)은 가상 데이터 시뮬레이션으로 정했다(5장).
- PRD에 없는 운영 정책(취소·노쇼·이용 제한·멤버십·성비·MBTI)은 주최 측 답변에 따라 팀이 정했다(6장).
- 가중치 설정 기능(MAT-15)은 PRD 6장에서 P1이지만, PRD 7.0·5장 운영자 흐름·17장 MVP 화면 목록에 따라 MVP에 포함했다. 회차별 설정과 서비스 전체 설정 중 MVP에서는 서비스 전체 설정을 우선 구현하고, 회차별 설정은 여유가 있으면 추가한다.
- 확정 후 취소 처리는 PRD 15장(대기자 자동 충원, 없으면 남은 참가자 자동 재배치)을 따르되, 대기자 자동 충원(STA-07)은 P1이므로 MVP에서는 P0인 자동 재배치(MAT-08)만 적용한다.
- PRD 15장은 취소 후 남은 인원 수를 구분하지 않는다. 재배치는 필수 조건을 충족하지 못할 때의 동작(PRD 7.0)이므로, 4명 이상이 남아 필수 조건을 충족하는 테이블은 유지하기로 했다.
