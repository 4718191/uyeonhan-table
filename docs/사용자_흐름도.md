# 사용자 흐름도

## 1. 문서 목적

`MVP_기능_범위.md`의 MVP 전체 범위를 참가자·시스템·운영자 흐름으로 그린다. 각 단계에는 화면 번호(MVP 문서 9장)와 PRD 기능 ID를 붙여, 화면 설계와 구현 순서를 정할 때 기준으로 쓴다.

### 범례

| 표시 | 의미 |
|---|---|
| 실선 상자 | 1단계(첫 시연 필수 흐름) |
| 점선 상자 | 2단계(MVP 완료 범위) |
| 마름모 | 분기 |
| `P-n` / `A-n` | 참가자 앱 화면 n번 / 운영자 웹 화면 n번 (MVP 문서 9장) |
| 🤖 | 운영자 개입 없이 시스템이 자동 처리 |

## 2. 전체 흐름 개요

정상 흐름은 참가자 행동과 시스템 자동 처리만으로 끝나고, 운영자는 사전 설정과 자동 처리되지 않은 예외만 맡는다.

## 3. 참가자 흐름

### 3.1 가입 → 신청 → 결제

```mermaid
flowchart TD
    A["웹앱 링크로 접속"] --> B["P-1 로그인·회원가입<br/>ACC-01"]
    B --> C["P-2 프로필·매칭 선호 입력<br/>기본 정보·MBTI·관심사·성향·식사 조건<br/>ACC-02~04"]
    C --> D{"필수 항목·개인정보 동의<br/>완료? ACC-05"}
    D -->|"아니요"| C
    D -->|"예"| E["P-3 모집 회차 확인·날짜 복수 선택<br/>APP-01·02"]
    E --> F{"서울 4개 지역 중<br/>1개 이상 선택?"}
    F -->|"아니요"| F2["현재 운영 지역 아님 안내<br/>다른 지역 오픈 알림 받기"]
    F -->|"예"| G["신청서 제출<br/>APP-03 · SUBMITTED"]
    G --> H["P-4 이용권 선택<br/>1회권 9,900원 / 멤버십 1·3·6개월<br/>APP-04"]
    H --> I["환불 규정·노쇼 정책 확인<br/>PAY-02"]
    I --> J{"모의 결제 성공?<br/>PAY-01"}
    J -->|"실패"| J2["결제 실패 안내·재시도<br/>FAILED"]
    J2 --> H
    J -->|"성공 · PAID"| K["P-5 신청 완료·매칭 대기<br/>매칭 발표 예정 시점 표시<br/>STA-01·02 · WAITING"]
    K --> KC{"매칭 마감(화요일 24:00)<br/>전에 신청 취소?"}
    KC -->|"예"| KC1["신청 취소 CANCELED<br/>1회권은 모의 환불<br/>멤버십은 신청만 취소"]
    KC -->|"아니요"| KM["마감 시 자동 매칭<br/>→ 4.1"]

    classDef s2 stroke-dasharray: 5 5
    class F2,KC,KC1 s2
```

- 매칭 마감 전 취소는 이 단계에서만 가능하다. 매칭이 화요일 24:00에 실행되므로, 확정 이후의 취소는 모두 마감 후 취소로 3.3·4.2에서 처리한다.
- 결제 대기(PENDING) 상태로 매칭 마감을 넘기면 매칭 후보에서 빠지고 결제 기한을 안내받는다(PRD 15장).
- 재신청 시 기존 프로필을 불러오는 기능(ACC-06)은 P1이라 MVP 범위 밖이다.

### 3.2 매칭 결과 확인

```mermaid

    B -->|"확정 CONFIRMED"| C["P-7 매칭 확정 상세<br/>날짜·식당·집합 시간·단체방<br/>INF-01·03"]
    B -->|"실패 ALTERNATIVE_OFFERED"| D["P-6 매칭 실패 해결<br/>실패 이유·대체 날짜·지역 확인<br/>STA-04 · MAT-12"]
    D --> E{"이용권 종류"}
    E -->|"1회권"| F{"해결 방식 선택<br/>STA-05"}
    F -->|"추천 일정 이동"| G["기존 결제 유지한 채<br/>새 회차 매칭 대기<br/>STA-06 · TRANSFERRED"]
    F -->|"이용권 보관"| H["이용권 보관<br/>다음 신청에 사용"]
    F -->|"환불"| I["모의 자동 환불<br/>REFUND_REQUESTED → REFUNDED<br/>PAY-03"]

    C --> L["3.3 행사 전·중·후로"]
```

- 대체 일정도 없으면 매칭 상태는 NO_MATCH가 되고, 1회권은 이용권 보관 또는 환불, 멤버십은 기한 연장으로 처리한다.
- 확정 결과에는 다른 참가자의 상세 개인정보나 점수를 보여주지 않고 제한된 소개만 보여준다(INF-06·MAT-12).

## 4. 시스템 자동 처리 흐름

### 4.1 자동 매칭 → 확정 → 안내

```mermaid
flowchart TD
    A["🤖 회차 마감 화요일 24:00<br/>스케줄러 자동 실행<br/>MAT-01 · MATCHING"] --> B["결제 완료·유효 신청자만 후보로<br/>서울 4개 지역 신청자"]
    B --> C["날짜·지역이 겹치는 사람끼리 후보군 구성<br/>MAT-02"]
    C --> D["차단·신고·비선호 관계 조합 제외<br/>MAT-05"]
    D --> E["나이 차 8살 이내 4~6인 조합 생성<br/>MAT-03"]
    E --> F["선호 조건 점수 계산·전체 최적화<br/>연령대→성비→MBTI→관심사→만나고 싶은 사람·새로운 사람<br/>MAT-04·06"]
    F --> G["7명 이상 분리·미완성 테이블 병합<br/>MAT-09"]
    G --> H{"필수 조건 충족<br/>+ 최소 점수 이상?<br/>MAT-07"}

    I --> J["식당 자동 배정<br/>지역·시간·인원·평점·예약 가능<br/>INF-02"]

    J1 -->|"아니요"| J2["같은 지역 다른 식당 탐색"]

    J3 -->|"아니요"| EX["운영자 예외로 전환<br/>식당 부족 · EXCEPTION"]
    J3 -->|"예"| K
    J1 -->|"예"| K["앱 단체방 생성·전원 초대<br/>INF-04"]
    K --> L["확정 안내 발송·공지 게시<br/>INF-01·05"]
    L --> L1{"발송 성공?"}
    L1 -->|"실패"| L2["자동 재시도<br/>INF-08"]
    L2 -->|"반복 실패"| EX2["운영자 예외로 전환<br/>발송 실패"]
```

- 같은 매칭 작업이 여러 번 실행돼도 테이블·환불·단체방이 중복 생성되지 않아야 한다(PRD 7.3).
- 재배치 중에도 연령·차단·신고 등 필수 조건은 완화하지 않고, 한 참가자를 두 테이블에 동시에 배치하지 않는다.

- 운영 대시보드의 상세 지표는 2단계에서 채운다. 1단계에서는 자동 처리 결과와 예외 목록 확인이 우선이다.

## 6. 상태 전이

PRD 12장에 따라 상태를 하나로 합치지 않고 분리해 저장한다. 아래는 흐름에서 가장 많이 바뀌는 매칭 상태와 결제 상태다.

### 6.1 매칭 상태

```mermaid
stateDiagram-v2
    [*] --> WAITING: 결제 완료
    WAITING --> MATCHING: 마감 시각 자동 실행
    MATCHING --> CONFIRMED: 필수 조건·최소 점수 통과
    MATCHING --> REALLOCATING: 4명 미만·조건 미충족·점수 미달
    REALLOCATING --> CONFIRMED: 재배치 성공
    REALLOCATING --> ALTERNATIVE_OFFERED: 재배치 실패
    ALTERNATIVE_OFFERED --> TRANSFERRED: 대체 일정 이동
    TRANSFERRED --> WAITING: 새 회차 매칭 대기
    ALTERNATIVE_OFFERED --> NO_MATCH: 대체 일정 없음·보관·환불·기한 연장
    MATCHING --> EXCEPTION: 자동 처리 실패
    REALLOCATING --> EXCEPTION: 자동 처리 실패
    CONFIRMED --> REALLOCATING: 확정 후 취소로 4명 미만
    CONFIRMED --> [*]
    NO_MATCH --> [*]
```

### 6.2 결제 상태

```mermaid
stateDiagram-v2
    [*] --> PENDING: 이용권 선택
    PENDING --> PAID: 모의 결제 성공
    PENDING --> FAILED: 모의 결제 실패
    FAILED --> PENDING: 재시도
    PAID --> REFUND_AVAILABLE: 매칭 불가·사전 취소
    REFUND_AVAILABLE --> REFUND_REQUESTED: 환불 선택
    REFUND_REQUESTED --> REFUND_PROCESSING: 자동 처리
    REFUND_PROCESSING --> REFUNDED: 완료
    REFUND_PROCESSING --> REFUND_FAILED: 실패 → 운영자 예외
```
